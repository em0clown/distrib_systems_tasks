### 1. В чем разница между ресурсом и коллекцией в REST API?

**Ресурс** - это отдельный объект, с которым работает API. Например, один пользователь с ID `5`.

**Коллекция** - это набор однотипных ресурсов. Например, все пользователи.

Пример адресов:

* `GET /users` - получить коллекцию пользователей.
* `GET /users/5` - получить одного пользователя.
* `POST /users` - создать нового пользователя в коллекции.

### 2. Почему для создания объекта используется POST и код 201, а не 200?

Метод `POST` обычно используется для создания нового ресурса на сервере.

Код `201 Created` означает, что ресурс успешно создан. Это более точное описание результата, чем `200 OK`, который означает лишь успешное выполнение запроса.

Например:

```http
POST /users
Content-Type: application/json

{
  "name": "Георгий"
}
```

Ответ:

```http
HTTP/1.1 201 Created
Content-Type: application/json

{
  "id": 5,
  "name": "Георгий"
}
```

Код `200` тоже может использоваться в некоторых API для создания, но `201` предпочтителен, когда действительно создан новый ресурс.

### 3. Что такое идемпотентность?

**Идемпотентность** - это свойство операции, при котором многократное выполнение одного и того же запроса имеет тот же предполагаемый эффект на состояние сервера, что и однократное выполнение.

Пример:

```http
PUT /users/5
```

Если отправить один и тот же запрос десять раз, пользователь всё равно будет иметь одни и те же данные.

Идемпотентные HTTP-методы:

* `GET`
* `HEAD`
* `PUT`
* `DELETE`
* `OPTIONS`
* `TRACE`

`POST` обычно неидемпотентен: повторная отправка может создать ещё один объект.

### 4. Почему ID обычно генерируется на сервере?

Сервер отвечает за уникальность идентификаторов и хранение объектов в базе данных.

Клиент отправляет данные:

```json
{
  "name": "Георгий"
}
```

Сервер создаёт объект, присваивает ему ID и возвращает результат:

```json
{
  "id": 5,
  "name": "Георгий"
}
```

Это позволяет избежать конфликтов ID между разными клиентами и гарантирует, что возвращённый идентификатор соответствует реально сохранённому объекту.

### 5. Что такое контракт API и почему важно его соблюдать?

**Контракт API** — это договорённость между клиентом и сервером о том, как они взаимодействуют.

Он определяет:

* адреса и HTTP-методы;
* структуру запросов и ответов;
* обязательные поля;
* типы данных;
* коды ошибок;
* правила авторизации.

Например, если сервер обещает возвращать поле `id` как число, клиент должен получать именно число, а не строку `"5"`.

Соблюдение контракта позволяет разным частям системы работать совместно и уменьшает количество ошибок при интеграции.

### 6. Зачем нужна спецификация OpenAPI (Swagger)?

OpenAPI - это стандарт описания HTTP API. Swagger UI - инструмент, который может отображать такую спецификацию в удобной интерактивной документации.

Спецификация нужна, чтобы команда имела единое описание API.

С её помощью можно:

* документировать методы и параметры;
* описывать модели данных;
* проверять соответствие реализации контракту;
* автоматически генерировать клиентский код;
* создавать интерактивную документацию для тестирования запросов.

Например, разработчик фронтенда может посмотреть спецификацию и узнать, какой запрос отправлять для создания пользователя, не изучая исходный код сервера.

**Итог:** REST API строится вокруг ресурсов и коллекций, HTTP-методы определяют тип операции, а контракт и OpenAPI помогают клиенту и серверу работать согласованно.
